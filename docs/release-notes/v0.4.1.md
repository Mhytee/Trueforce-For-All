# v0.4.1: Wheels that switched themselves off and on now stay on

A fix for RS50, G PRO and G923 owners whose wheel started power cycling on
v0.4.0. If you turned your wheel on with SimHub already open and it switched
itself off and back on again, with a jolt through the rim as it came back,
this release stops it.

### Your wheel stops switching itself off and on

v0.4.0 added a repair for one specific fault: if the USB capture that reads a
game's force feedback starts up without being able to see your wheel, none of
the game's force reaches the plugin, and switching the wheel's USB port off
and on again is the only thing that fixes it. That repair worked. The problem
was when it decided it was needed.

- **It was checking too early.** The check ran on a fixed timer, but the capture it was checking takes as long as it takes to start, because it has to scan every USB controller on your PC before it knows which one your wheel is on. On a PC with several controllers the check finished first and found nothing, for the simple reason that nothing had started looking yet. A perfectly healthy wheel was declared unreadable and its port was cycled, which the wheel feels as being switched off and on.
- **It now waits for the capture to actually be running**, gives it a moment to settle, and only draws a conclusion once the capture has been listening for the whole measurement. If the capture never comes up, nothing is concluded and nothing is cycled.
- **It also checks again that you are not driving** in the moment before it acts, so the check can no longer straddle you starting a session.
- **There is now a switch for it.** Settings, Force Feedback (Advanced): "Reconnect the wheel automatically if force feedback capture starts up blind". On by default, because it does rescue a real fault. Turn it off if you would rather the plugin never cycled your wheel's port, and if you do, FFB pass-through may stay dead until you replug the wheel yourself.

### Clearer answers when USBPcap will not start

USBPcap is the component that lets the plugin read a game's force feedback
over USB. When it is installed but never loads, there are two quite different
reasons, and until now the plugin could not tell you which one you had.

- **The self-test now says which.** Either Windows is never asking for the capture driver, or Windows is asking and something is refusing. They need different fixes, and the difference is not something you could reasonably be expected to work out.
- **Reinstalling does not always help, and now the plugin says so.** USBPcap's installer stops the moment it finds an existing install, so reinstalling over a broken one does nothing at all. The plugin used to run it, report success and send you to restart for a repair that never happened.
- **A new Uninstall button appears for the one case it fixes.** It runs USBPcap's own uninstaller, which is the step that was missing. You restart, press Reinstall, and restart once more. It stays hidden on a healthy machine, and on a machine that has simply not restarted since installing USBPcap.
- **USBPcap installed somewhere other than Program Files is now found by itself**, instead of waiting for you to point the plugin at it.
- **Support logs carry all of this**, so a report no longer depends on anyone running registry commands by hand.
